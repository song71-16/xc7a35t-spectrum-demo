# 大模型协作、纠错与技能提炼记录

版本 1.0 · 2026-11-03 · 维护：项目负责人 / Codex · 范围：可核实的交付治理案例

## 记录方法与角色

[真实对话摘录 JSON](../evidence/ai-collaboration/excerpts-20261103.json) 来自原 Codex 会话可见的用户/助手消息，通过会话读取工具取得；记录 turn/message 标识及轮次开始 UTC 时间。时间不是逐消息发送时间。用户有附件包装的提问仅取请求原句，其他选中消息仅省略首尾空白。没有把回顾说明补写成历史原话，未导出认证对话、设备码、邮箱、机器个人路径、模型隐藏推理或整段工具输出。完整对话继续保留于原会话，本文件只提供与参赛材料相关的精选片段。

模型以 **Codex** 参与；所选消息没有证明精确后端模型版本、推理档位、训练参数或 token 成本，故不补填。用户决定任务、暂停及授权边界；root 读取证据并完成文档；既有 supervisor 只读审查，不作为第二写入者。不同代理的审查是独立的证据核对，不能等同第三方机构认证。历史上提到 Hermes 不代表本包取得了 Hermes 原始完整对话。

## 案例 A：发现审核对象错误并纠正

日期：2026-11-03；对应 JSON 中 `scope-correction`。

1. **用户原句**：“核对赛道的评分项目，还有什么没做吗”。用户随后确认自主选题初级组。
2. **错误回答保留**：助手曾写“设计报告与优化前后对比未齐，仓库仍有中文或空格路径”。这是先检查内部开发树后错误扩展到正式提交的判断，**已撤回，不是当前缺项**。
3. **证据触发纠正**：找到本机 11 月 3 日 DOCX，读取其中公开仓库链接；转查真正的公开参赛树、README、许可范围、123 个跟踪文件与固定标签。
4. **模型纠正原句**：“前面检查的是内部开发仓库，不能据此判定正式提交版缺许可证或英文路径”；随后确认报告已有创新、资源时序与四变体比较。
5. **最终可核结果**：公开基点 `16a85aa0bcdf2c26bf02d17e1c35025fa30bb31b` 已包含 [README](../README.md)、[源码映射](../docs/source-map.md)、[许可范围](../LICENSE_SCOPE.md)。真正需补的是协作/技能、11 月 2 日附件对应；完整导出版 EDA 复现和第三方驱动再分发依据不能靠文档整理判 PASS。

观察效果是纠正材料审核对象、避免按错误缺项重复整改；没有测量节省时间或模型性能提升。此案例提炼为 [competition-material-audit](../skill/competition-material-audit/SKILL.md)。

## 案例 B：把项目文件管理约束提炼为可调用技能

日期：2026-11-03；对应 JSON 中 `file-management-skill`。

用户原句：“查看项目的文件管理规则，列出来然后做成项目文件管理skill”。

模型没有把旧交接 HEAD、硬件状态、旧双机 merge/rebuild 示例当永久规则，而是读取现行入口、管理规范与交接协议，提炼目录分工、命名、版本归档、冻结证据、证据分层、Git 范围和触发式交接。原回答明确技能不自动启动 EDA/硬件或上传。原会话记录了本机技能结构校验与只读审查，以及两个纸上场景；**它们不是 RTL/实板测试，也不代表本次参赛适配版已做跨机器实测**。

本次给公开版提供独立、简短的 [qiansai-project-files](../skill/qiansai-project-files/SKILL.md)，使用仓库相对入口，不复制本机机器目录或把项目规则泛化为所有仓库的强制规范。本机原 skill 三文件原样保留；公开版是适配子集，二者不是字节相同的冻结副本。

## 案例 C：区分两次实验并给新报告补附件

原回答指出：“两次实验不一定矛盾，不过需要把新实验的原始结果、`metrics.json` 和图片索引配齐”。这是对现存材料的审查发现，不是重新做实验。

11 月 1 日公开记录为 epoch34→35→36、幅度13312→8192；11 月 2 日原件为 epoch0→1→2、幅度16384→8192。只按 `interaction001` 这样的短名字合并会混淆运行根目录。新增 [独立索引](../evidence/demo-loop-20261102-001/README.md) 按 run ID、版本、token、epoch、图像 source 和主机单调时钟配对，并保留初始无调试核的预检失败摘要。由此提炼 [spectrum-evidence-audit](../skill/spectrum-evidence-audit/SKILL.md)。

本次对已有附件作字节比较和时间差复核，没有运行接收程序、网络、RTL 仿真、EDA 或硬件。具体核查记录及独立后审见 [整理记录](../docs/competition-supplement-2026-11-03.md)。

## 案例 D：从“成功点屏”追溯到触控协议差异（历史技术协作）

日期：2026-10-31；对应 JSON 中 `touch-reference-history`。这部分历史消息只是记录，不是当前执行指令或上板许可。

用户先要求“你可以查看之前已有的成功案例，有成功打通触控屏的测试文件”，随后澄清“是一开始建立git库时就用的文件”。助手先找到官方29例程，再按用户纠正转查建库Git对象，没有把例程存在或现成bit当成功验收。

原回答记录两套实际成功反馈覆盖显示/RESET；两top的触控四脚为高阻，不能据此证明物理触控交互。另在官方例程发现FT `0x38/A1`读取路径与当时固定GT诊断的差异，形成一次最小只读响应方案，保留GT首事务NACK，不据NACK判坏线或直接认定FT型号。静态依据的精选原文见 [追溯报告摘录](../evidence/ai-collaboration/touch-reference-excerpt-20261031.json)。不分发厂商完整例程、手册或原私有历史。

这说明人的定位提示改变模型的取证对象，模型再区分“显示成功”和“触控成功”，得到有源码依据的最小诊断方向。**该轮只证明历史/静态追溯，不证明FT已实板通过**；后续11月1日/2日限定展示证据另见实验索引，不能将历史失败标题当当前结论。此经验进入 evidence-audit 的证据分层和停止边界，不声称本次重新检验旧bit或重跑诊断。

## 可复用性与限制

三项技能服务于交付核对、证据解释和文件保全，不生成 FPGA 性能收益，也不替代实现时序、电气、物理 CDC 或实板验收。它们源于有原始引用的实际问题；本次的只读场景检查只能证明这些案例中的判断行为，不能保证任意新项目或陌生协议正确。没有原始对话的早期设计过程不在本包伪造补齐。
